# sticky-todo 检查更新与自动更新设计文档

日期：2026-09-28
状态：已与用户确认

## 1. 背景与目标

程序目前靠手动下载新 exe 更新：用户得自己发现新版本、自己下载、自己覆盖。本设计给应用加上「检查更新」与「自动更新」，同时保持它最重要的形态特征——**单文件裸 exe，不需要安装**。

据此选定的路线是自建更新（不走 `tauri-plugin-updater` + 安装包）：检查走 GitHub Releases API，下载后由辅助脚本在进程退出后覆盖自身再重启。

### 目标

1. 启动后自动检查更新，之后每 6 小时一次；设置里可以关掉自动检查。
2. 发现新版本自动下载并校验完整性，下载完成前不打扰用户。
3. 用户点「更新并重启」后完成替换与重启；失败可恢复、可追溯。
4. 保持不需要安装包的分发形态，不引入代码签名体系。

### 非目标

- 不做增量更新（每次下载完整 exe，约 3.9 MB）。
- 不做后台静默安装（永远要用户点一下才换文件）。
- 不做灰度、回滚、多通道（beta/stable）。
- 不做代码签名；因此校验只能证明「文件没坏」，不能证明「文件没被换过」。
- 不把更新状态写进 `data.json`（它会被同步到别的机器，与本机状态无关）。

## 2. 更新源与版本比较

- 端点默认 `https://api.github.com/repos/monk233/sticky-todo/releases/latest`。
- 端点可被环境变量 `STICKY_TODO_UPDATE_ENDPOINT` 覆盖（开发与测试用，也方便换镜像）。
- 仓库是公开仓库，不需要 token。GitHub 的 `latest` 本身跳过 draft 与 prerelease。
- 取 `tag_name`（形如 `v1.4.0`），去掉开头的 `v`，与当前版本比较。当前版本取自编译期写入的 `CARGO_PKG_VERSION`。
- 比较规则：按 `.` 分段，逐段转成整数后比较，缺段按 0 补，非数字段按 0 处理（容错，不panic）。远端严格大于当前才算有更新。
- 从 `assets` 里取名为 `sticky-todo.exe` 的资产，读它的 `browser_download_url`、`size` 与 `digest`（形如 `sha256:4d1f766d…`）。

## 3. 检查、下载与校验

时机：

- 启动后延迟 8 秒检查一次（避免与应用启动争资源）。
- 之后每 6 小时一次。
- 自动检查开关关闭时不排期；手动点「检查更新」始终可用。

下载：

- 目标路径 `<数据目录>/updates/sticky-todo-<版本>.exe`，先写 `.part` 后缀，完成校验后再改名。
- 下载过程中通过事件 `app://update-progress` 上报 `{ downloaded, total }`，前端据此显示百分比。
- 校验：下载完用 `digest` 里的 SHA-256 比对文件。不一致则删除文件并报错。摘要缺失时跳过校验，但结果里标注 `verified: false`，界面显示「未校验」。
- 启动时清理 `updates/` 下残留的 `.part` 文件。

失败处理：离线、超时、限速、404 一律当作「检查失败」，只记录原因与时间供设置面板显示，不弹窗、不打断。

## 4. 安装（覆盖自身并重启）

用户点「更新并重启」后：

1. 把下载好的 exe 复制到 `%TEMP%\sticky-todo-<版本>.exe`（避开数据目录被同步占用的情况）。
2. 生成 `%TEMP%\sticky-todo-update-<时间戳>.cmd`，内容是：等待当前进程退出 → `move /y` 新 exe 到当前 exe 路径 → 启动新 exe → 写结果文件 → 删除脚本自身。
3. 用 `cmd /c` 以隐藏窗口方式启动该脚本。
4. 应用调用 `app.exit(0)` 退出。

结果文件写在 `<数据目录>/updates/last-install.txt`，内容为 `ok` 或 `failed:<原因>`。下次启动时读取：

- `failed:` 开头 → 提示「自动替换失败，请手动替换」并给出新 exe 的路径，提示保留到用户关闭。
- `ok` → 删除结果文件与 `updates/` 下的旧包，并提示「已更新到 x.y.z」。

前提与边界：exe 所在目录必须可写。放在 `C:\Program Files` 这类需要提权的目录时 `move` 会失败，走上面的失败提示路径；原 exe 不会被先删掉，因此不会出现两个都没有的情况。

## 5. 界面

设置面板新增「更新」分区：

- 当前版本（只读）
- 「自动检查更新」开关
- 「检查更新」按钮 + 状态行，取值：`正在检查…` / `已是最新（检查于 20:41）` / `发现 v1.4.0，正在下载 42%` / `已下载 v1.4.0，可以更新` / `检查失败：<原因>`
- 有已下载版本时出现「更新并重启」按钮
- 「打开 Releases 页面」按钮（网络不通时的兜底入口）
- 校验失败或摘要缺失时，状态行里明确标注「未校验」

托盘右键菜单增加「检查更新」一项。

侧栏底部的设置图标在有已下载版本时显示一个小圆点。

## 6. 状态存放

- 已下载版本、下载进度、上次检查结果都只放内存，重启后重新检查（3.9 MB，几秒）。
- 「自动检查更新」开关写进 `config.json`（本机偏好，与 `dataDir` 同类），加 `autoCheckUpdate` 字段与读写命令。

## 7. 依赖与实现分工

- 新增 Rust 依赖 `ureq`（rustls），负责检查与下载；SHA-256 复用已有的 `sha2`、`hex`。
- 检查、下载、校验、生成替换脚本全在 Rust 侧；前端只负责展示与触发。
- 这样 CSP 不需要放宽，几 MB 的数据不必过 IPC，核心逻辑可以用 `cargo test` 覆盖。
- 备选方案（若实测体积增量不可接受）：前端 `fetch` 检查 + 下载字节走 IPC，与现有导入剪贴板图片同一条路；代价是 CSP 要放开到 `api.github.com`，且 3.9 MB 要序列化一遍。

## 8. 测试策略

### 8.1 Rust 单元测试

- 版本比较：`1.3.0` vs `1.3.0`、`1.3.0` vs `1.4.0`、`1.3.0` vs `1.3.1`、`1.10.0` vs `1.9.9`（数值而非字典序）、缺段 `1.3` vs `1.3.0`、带 `v` 前缀、非数字段。
- 解析 GitHub 返回的 JSON：正常、缺 `assets`、缺 `digest`、`assets` 里没有 exe、非法 JSON。
- 替换脚本生成：内容包含新 exe 路径、当前 exe 路径、结果文件路径；路径含空格时加引号。
- 结果文件解析：`ok` / `failed:原因` / 空文件 / 不存在。

### 8.2 手动与端到端验收

- 用 `STICKY_TODO_UPDATE_ENDPOINT` 指向本地 mock：检查到更高版本 → 下载 → 校验 → 覆盖自身 → 重启 → 界面版本号变化。
- 校验不通过（故意改摘要）时删除文件并报错，不执行替换。
- 离线时检查失败只写状态，不弹窗。
- 把 exe 放到只读目录后触发更新，替换失败 → 下次启动出现「请手动替换」提示，原 exe 仍可运行。
- 关掉自动检查后启动不再自动查，点按钮仍可查。
